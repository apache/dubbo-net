# RFC 约定

[English](../en/rfc.md) · [中文首页](index.md) · [变更索引](../../CHANGELOG.md)

仅在存在真实架构决策、备选方案与取舍时编写 RFC。RFC 解释**为什么**作出决定；当前**实际行为**仍以代码和测试为准。进度交给关联 Issue 和 PR 追踪，不用 RFC 维护施工日志，也不为待办功能预造空 RFC。

## 编号与发布

- 首次提出方案时取下一个未使用的四位编号（例如 `0001`），编号不复用。需要面向两种语言读者的决定，在**同一 PR** 中创建 `Docs/en/rfcs/0001-topic.md` 和 `Docs/zh/rfcs/0001-topic.md`，两版编号、状态、决定及关联链接一致。主题用简短的小写连字符形式；仅在确有提案时创建 `rfcs/` 目录。翻译修正仍沿用原编号，并关联修改 PR。
- `Proposed`：备选方案讨论中。`Accepted`：决策得到确认。`Superseded`：被已链接的 RFC 取代。`Withdrawn`：提案被放弃。不能仅凭已有代码把提案标成已接受；决策与实施分别关联。状态或结论变化时同步两种语言。

## 最小模板

仅在起草实际 RFC 时使用下列大纲。关联具体 Issue、决策讨论和**已有的**实施 PR/commit；尚未实施时明确写明。接受设计不等于代码已经发布。

```markdown
# RFC-NNNN：简短标题

状态：Proposed | Accepted | Superseded | Withdrawn
问题：链接
决策／评审：链接或“待确认”
实施：PR/commit 链接或“尚未实施”

## 背景与约束
现有问题是什么，哪些兼容性必须保留？

## 方案与取舍
列出选定方案和至少一个真实备选方案，说明成本。

## 决定
写下已记录的选择；仍为 Proposed 时写“待确认”。

## 后果
记录限制和后续工作，不宣称未发布的行为。
```
